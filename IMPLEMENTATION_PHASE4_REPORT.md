## 3. Frozen Generation Parameters & Timeout Governance

### 3.1 Deterministic Generation Configuration
In strict compliance with `P0_ARCHITECTURE_CONTRACT_FREEZE_REV2A` (Suite 23), generation parameters are completely locked:

```python
OPTIONS = {

    "seed": 42,
    "top_p": 1.0,

```

Zero retries (`retries=0`) ensures that non-deterministic regeneration loops are strictly prohibited. Any failure or rejection triggers deterministic fallback immediately.

### 3.2 Timeout Governance (Suite 24)
- **Production Default**: 120.0 seconds.
- **Formal Benchmark Default**: 120.0 seconds.
- **Configurability**: Configurable via the `LLM_TIMEOUT_SECONDS` environment variable (e.g. `LLM_TIMEOUT_SECONDS=45` for quick test runs).
- **Timeout Behavior**: When an LLM request exceeds the timeout threshold, execution does not retry or hang. The service catches the timeout exception and immediately produces a `DETERMINISTIC_FALLBACK` report with `fallback_reason="LLM_TIMEOUT"`.

## 4. Patch 001 Grounding Validator Architecture

The candidate JSON output generated by Llama 3.1 8B must parse into the canonical `LLMReport` schema:
- `coach_summary`: `List[str]`
- `observed_evidence`: `List[str]`
- `limitations_and_confidence`: `List[str]`
- `session_level_recommendations`: `List[str]`
- `technical_note`: `List[str]`

The parsed candidate report is then subjected to `Patch001GroundingValidator` (`backend/app/services/grounding_validator.py`), which executes all 8 deterministic validation gates:

### Gate 1: Physical Player Attribution Prohibition
- **Rule**: In automated analysis mode, automated persistent identity is uncertified (`FAIL_UNSAFE_MERGE`). Player-specific naming (e.g., "Player 1", "No. 4", "the midfielder John") is strictly forbidden.
- **Permitted**: Anonymous track identifiers (`track_3`, `track_7`) and `UNRESOLVED_TARGET`.

### Gate 2: Tone and Blame Prohibition
- **Rule**: Rejects subjective, judgmental, psychological, or disciplinary language (e.g. "lazy", "failed", "blame", "disappointing", "careless", "fault", "punish").
- **Requirement**: Tactical coaching reports must maintain neutral, descriptive, observational tone.

### Gate 3: Participant Privacy Preservation
- **Rule**: Rejects any occurrence of unredacted private participant names or identifiers from research sessions.

### Gate 4: Numeric Grounding (`all_numbers_patched`)
- **Rule**: Every numeric value (integers and floats) appearing anywhere in the candidate report must be grounded in the input `StructuredEvidencePayload`.
- **Implementation**: The validator performs recursive leaf traversal of the entire payload (`evidence_items`, kinematics, window timestamps, frame counts, summary stats). Any ungrounded number triggers an immediate `UNGROUNDED_NUMERIC_CLAIM` violation.

### Gate 5: Negation-Aware Target Attribution
- **Rule**: When coach instruction targets are `UNRESOLVED_TARGET`, affirmative claims that an individual complied or failed to comply are forbidden.
- **Implementation**: Implements negation-aware regex parsing. Affirmative attributions (e.g. `track_3 complied with the instruction`) are rejected, while negative or explanatory limitations (e.g. `no physical player could be confirmed as the target`) are safely permitted.

### Gate 6: Kinematics Integrity & Metric Suppression
- **Rule**: When metric calibration is inactive (`NO_METRIC_CALIBRATION` or `GEOMETRIC_SOLVE_ONLY`), physical metric claims (e.g. `12.5 m`, `18.2 km/h`) are suppressed and forbidden from LLM claims. Speeds cannot be inferred across missing tracking observations.

### Gate 7: Tactical Category Grounding
- **Rule**: Any tactical category mentioned in the report (Defensive, Offensive, Pressing, Passing, Positioning / Hold Ground) must be present in the underlying extracted tactical events. Invented categories (e.g. "Set Piece", "Goalkeeping") are rejected.

### Gate 8: Tactical Action Grounding
- **Rule**: Any tactical action mentioned in the report must correspond to an action present in the extracted events (e.g., "mark", "press", "hold ground"). Invented actions (e.g., "slide tackle", "dribble", "bicycle kick") are rejected.

## 5. Deterministic Fallback Report Engine

The system provides a 100% fail-closed deterministic fallback engine (`backend/app/services/deterministic_report_service.py`):
1. **Activation Triggers**:
   - Local Ollama service unreachable / connection error.
   - Cryptographic model digest mismatch or prompt tampering.
   - HTTP generation timeout ($> 120$s).
   - Non-JSON or schema-invalid candidate LLM output.
   - Any grounding gate failure in `Patch001GroundingValidator`.
   - Explicit pipeline configuration (`pipeline.run_pipeline(..., force_deterministic_fallback=True)`).
2. **Deterministic Properties**:
   - Zero LLM calls required.
   - Compiles structured Markdown report directly from `StructuredEvidencePayload`.
   - Produces byte-identical output for identical evidence inputs across repeated runs.
   - Fully enforces metric suppression (no spurious metre or km/h tokens in uncalibrated sessions).
   - Fully enforces track anonymity under `FAIL_UNSAFE_MERGE`.

## 8. Scientific Boundaries & Non-Regressions

4. **Scope Boundaries Preserved**: Modal cloud worker deployment, full 340s session processing, Supabase persistence, and Oracle showcase rerenders remain strictly unstarted.
